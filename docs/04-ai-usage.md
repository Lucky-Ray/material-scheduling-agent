# 04 个人贡献与 AI 辅助说明

## 1. 协作方式

本项目采用“本人审阅与提出修改要求，AI 辅助方案细化、实现和执行”的协作方式。我主要负责检查交付是否完整、指出需要整改的问题，并确定工程整理和仓库交付方式；Codex 辅助提出具体技术方案、编写代码、整理文档及执行验证。

以下按实际参与的工作说明分工，不将方案审阅等同于亲自编写代码，也不将 AI 执行测试表述为本人手动执行。

## 2. 我的实际贡献

### 2.1 交付质量审阅与问题识别

我审阅了首版交付，指出其详细文档不足，不能仅凭已有几个文档文件就视为完成交付。我要求将需求、设计、评估、AI 使用和复盘进一步展开，使评审能够核对设计依据、验收点与实际证据。

这项反馈推动文档从简要说明改为包括输入输出契约、工具职责、成功标准、场景映射、预期与实际结果以及已知限制的完整材料。

### 2.2 工程独立性与资料组织要求

我提出将项目与面试准备工作区分离，作为独立工程整理，避免其他面试资料混入交付。在这一要求下，项目迁移到独立目录，代码按模型接入、业务工具、执行循环和 CLI 拆分，并保留统一入口。

我的贡献是提出独立交付和清晰组织的要求；模块划分的具体实现、文件迁移和运行检查由 AI 辅助完成。

### 2.3 迭代方向与交付推进

我对首版结果提出继续完善的要求，推动补齐详细材料及交付检查，避免停留在仅能演示的初稿。我持续检查交付进展，并提出 GitHub 上传、访问方式和提交材料准备等后续要求。

请求级幂等、规则变化复核、聚合输出、CLI 错误处理等具体技术补强由 AI 提出并实现，不作为我独立设计或亲自编码的成果。

### 2.4 仓库访问与提交方式决策

我要求将工程上传 GitHub，并在没有指定评审账号的情况下决定使用公开仓库，方便评审直接访问。我还提出准备可上传的项目归档和提交信息。仓库创建、Git 提交、推送、归档及页面填写由 AI 协助执行。

### 2.5 当前验证范围的取舍

我选择本轮暂不运行真实模型验证。项目因此保留远端模型接入入口，但当前验证记录仅覆盖离线流程；这一取舍意味着真实模型动态决策效果尚未得到证明，不能据此声称完整满足该项验收。

## 3. AI 辅助的具体范围

| 工作项 | AI 负责的内容 | 可核对材料 |
| --- | --- | --- |
| 方案细化 | 工具协议、有界执行循环、状态和约束设计 | docs/02-solution.md、src/runner.py |
| 编码实现 | 模型适配、CLI、规则工具、SQLite 存储和请求级幂等 | src/ |
| 合成资料 | 素材、标签规则、时段和已有占用 | data/catalog.json |
| 验证执行 | 编写测试、注入失败、生成场景记录并运行验证 | tests/、examples/、scripts/verify.py |
| 文档整理 | 根据本人反馈扩写需求、方案、评估、贡献说明和复盘 | docs/ |
| 工程与仓库操作 | 移动目录、拆分模块、创建仓库、提交推送、配置 CI、生成归档 | Git 历史、.github/workflows/tests.yml |

没有从面试工作区的其他项目复制业务代码。具体实现与执行记录可通过仓库核对。

## 4. 验证结果与边界

已执行的工程验证由 AI 辅助完成：19 项单元测试、12 组离线场景断言通过；GitHub Actions 的 Python 3.10、3.12 两个任务均通过。实际日志和输入输出保存在 examples，验证详情见 docs/03-evaluation.md。

开发辅助工具 Codex 与运行时业务模型是不同角色。MockModel 是确定性离线模拟器，不是真实业务模型；现有运行记录均明确标记 mode=mock。当前未进行真实模型效果验证、真实发布或线上部署。

我的已记录贡献集中在交付审阅、整改要求、工程独立性和仓库交付决策；目前没有可核对的本人独立代码修改或本人手动执行测试记录，因此不作此类声明。

## 5. 实际用时与后续复核

当前材料未填报精确的个人实际投入时间，不将 AI 自动执行时长、对话跨度或题目建议时长替代为个人工作用时。

后续需要本人复核的内容包括：能否解释硬性时间与待确认边界、请求级幂等与事务重查的作用，能否根据 Trace 判断保存是否成功，以及是否补充真实模型的运行证据。尚未完成的复核不记为既有个人成果。

## 6. 数据与公开材料

项目使用合成素材和时段；.env.example 仅含占位配置。仓库忽略 .env、SQLite 运行数据库和 Python 缓存，未包含题目截图或完整试卷文本。GitHub 仓库按本人决定公开，提交用 URL 和最终 SHA 应与实际远端版本保持一致。
