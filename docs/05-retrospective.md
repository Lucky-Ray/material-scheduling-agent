# 05 工程复盘与后续计划

## 1. 复盘边界

本文件记录工程层面的设计难点、实际改动和剩余工作。它不代写候选人的个人学习经历，也不把尚未进行的真实模型测试写成已完成成果。个人感受和实际投入时间在末尾由本人补充。

## 2. 本轮发现的问题与改进

上一版虽然有五个文档文件，但说明过于简短，缺少验收映射、工具协议、证据索引、真实模型验证步骤和限制分析。代码也集中在 agent.py，项目放在面试工作区中，独立交付边界不清楚。

本轮将项目移到同级独立目录，拆分模型、业务工具、执行器、CLI，保留原命令入口。五份核心文档补成可以对应代码和证据的说明，另增加提交检查表与场景索引。新增缺版权、无槽位、占用变化、规则变化、步数上限等运行记录，并保存各场景数据快照。

这些改动改善可检查性和复现性；不能据此声称真实模型验收已经完成。

## 3. 难点一：模型能建议，工具仍需校验

若只在提示词中写“不要更改硬性时间”，模型仍可能输出错误 slot。当前选择在 save_draft 内重新检查 hard_time、请求时间和可用性。即使模型选择了错误动作，工具也应返回明确拒绝结果。

收获：模型决策与权限执行需要不同职责。测试不能只覆盖理想提示词路径，应直接调用工具尝试越界，核对它是否独立阻断。

## 4. 难点二：幂等重放与自己的占用

草稿保存后会占用时段。若重复请求先查询占用而没有识别旧草稿，就可能把自己的时段当成外部冲突。当前查询返回 existing，模拟器优先恢复已有草稿；保存工具按相同载荷哈希直接返回旧结果。

本轮修复：幂等键改为显式 request_id 或素材+原时间，不再包含候选 slot；新建 requests 映射表并在同一事务中写入。重放前重新检查当前规则。新增测试覆盖改 slot 防重、请求 ID 挪用、规则变化和旧库迁移。仍未实现历史草稿自动撤回和审批状态更新。

## 5. 难点三：成功是工具事实

读素材、检查规则、找到时段都不能证明已经保存。当前最终状态必须对应保存工具证据；没有成功证据时不能仅凭模型 finish=completed 认定完成。保存故障测试检查 ok=false、failed 和数据库零条。

另一个边界是“失败不一定无副作用”：如果已经保存，后续模型请求异常或超过上限，当前执行器会返回 failed / incomplete，但草稿仍可能存在。本轮已增加 material_result.save_status，并让所有退出路径保留成功 draft，便于调用者分别判断保存事实与执行状态。

## 6. 难点四：真实模型和 Mock 证据不同

固定分支可以稳定地验证流程和数据库约束，但没有验证模型会根据观察作决策。当前明确使用 mode=mock 标注离线记录，并保留远端模型接入与两条 live 验证命令。

收获：可运行的 Agent 框架、业务工具正确、真实模型效果是三个层次。测试报告应分别给出事实和缺口，不能把一种证据扩大到另一种结论。

## 7. 为什么先做这些取舍

使用 CLI 避免 UI 工作挤占核心闭环验证；使用 SQLite 提供最小持久化与事务；使用标准库降低安装门槛；使用合成数据稳定触发风险、冲突和失败。

对应代价是：不具备真实审核语义、复杂排期资源模型、生产监控或跨机器状态。后续扩展必须先明确业务目标，不能直接将演示代码描述为生产系统。
